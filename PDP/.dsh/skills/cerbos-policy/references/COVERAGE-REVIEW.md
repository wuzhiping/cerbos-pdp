# 独立覆盖审查

写完策略包后，用这份说明交给一位全新的、只读的审查者。请提供：原始且已确认的需求（逐字照抄）、策略包路径，以及这份说明。把生成者的计划和审计排除在审查说明之外，免得它们的疏漏变成这次审查的范围。审查者只负责分析；所有修复由上游负责。除非用户另有指定，使用当前模型。

## 审查者的任务

先根据已确认的需求推导出必需的测试用例，再去读生成的测试。不要再委派。产出一张包含以下列的表：

```text
Resource | Grant path | Action | Prerequisite or boundary | Required request facts | Expected effect | Existing assertion or gap
```

对每一个消费它的资源和动作，把每条放行路径分别展开。同一个共享条件可能在一处放行路径上接对了、在另一处漏掉了，所以覆盖了一条路径并不能证明其他路径也被覆盖。

对每条路径，在其他前提都保持满足的前提下，为每个互相独立的前提各推导出一个 ALLOW 用例和一个 DENY 用例。要覆盖缺失的必需基础角色（用属性匹配但角色无关的无关角色来构造）、租户隔离，以及需求指定的各种关系条件或状态条件。做这些否定用例时，让其他放行路径保持不激活。此外还要推导必需的边界值、可选属性的默认值、会改变决策的覆盖、重叠的放行、显式拒绝，以及默认被拒的动作。对于派生角色，要包含调用方给出的、绝不能授予访问权的派生角色名。对于只在部分 scope 中存在的规则或限制，把由它决定的请求在每个不含它的 scope 中重跑一遍，期望得到相反的效果。

然后检查策略、测试和解析后的 fixture。只有当某条断言确实覆盖了预期的资源、动作、效果和前提时，才填最后一列。要比对真实的 principal ID、角色和资源属性；标签和测试名不算证据。一个同时违反多个前提的否定用例，说明不了到底是哪个前提导致拒绝。

交回完整的表格，随后列出具体的缺口，附上文件引用和最小化的 fixture/测试修复方案。只有当每一行推导出的用例都有证据支撑时，才可以报告审查通过。不要修改文件，不要放宽需求，也不要拿生成者的通过数量当作完整性结论。
